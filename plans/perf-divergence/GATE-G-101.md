## Protocol deviation (read this first)

`plan/DECISIONS.md` D-110 specifies a controlled matrix run via
`scripts/perf/run-matrix.mjs`: a dedicated serial machine (no other CPU-heavy work),
power-plan pinned to High Performance, interleaved config order, cool-downs between
runs, a fresh Playwright browser launch per run, and CPU-frequency sampling for drift
detection — executed against the repo's own synthetic/golden fixtures.

None of that happened here. Instead, mid-plan, the user asked for a standalone local
perf-check page (`perf/standalone/`, deployed to GitHub Pages) so real numbers could
come from actual hardware instead of this session's cloud execution container (which
can't represent `plan/ENVIRONMENT.md`'s pinned reference laptop). Real records were
then gathered by hand, one click at a time, on the user's own laptop, against **one
real ~4.55-minute song** (not the repo's synthetic fixture) — see the "How the data
was collected" table below for exactly what differed from D-110 on each run.

This means: no drift/thermal monitoring was performed (D-110 rule 6/7 don't apply —
there's nothing to report there); some `webgpu-standard` repeats ran in the same
browser tab as the previous one rather than a fresh launch, which measurably speeds
up shader-compile and cache-hash costs between repeats (see per-run notes below); and
the content-dependence check (A-107, comparing a synthetic vs. real-music input) was
never performed, since only one real song was used throughout.

None of this makes the numbers wrong — they're real measurements of real inference on
real hardware — but they are a smaller, less controlled sample than the plan
specifies, and every row below states its exact sample size.
